Thank you for your interest in contributing!

To keep the project maintainable and avoid unnecessary review overhead or conflicts, please follow these rules when submitting changes.

## 📜 Code of Conduct

Be respectful and constructive. Harassment, hostility, or disruptive behavior will not be tolerated. We will also not tolerate any hate speech, racism, homophobia or any other forms of discrimination.

Be aware that your contribution may be rejected for any number of reasons. It's not personal, so don't take it that way.

---

## 🚦 Contribution Rules

### 1. Original, human-written work only
- All contributions must be written **entirely by a human.**
- Code generated by AI may not be "rewritten" to make it "human". **If you do not know what the code you are submitting is doing, it doesn't belong here.**
- No **ChatGPT / Copilot / Bard / Claude / etc**. generated code, tests, docs, comments, or commit messages.
- PRs suspected of being **AI-generated** will be rejected.
- The only exception is translations. Most translation services use some form of AI, so this is unavoidable.

### 2. No copied code unless licensing is fully verified
To avoid legal issues:
- External code must come from a license **compatible** with this project.
- Required attribution must be included.
- If the license is unclear, you must provide **explicit written permission** from the owner.
- Code of unknown or unverifiable origin will be rejected.

### 3. Contribution Licensing
By submitting a pull request:
- You agree that your contribution is licensed under this project's license (see `LICENSE`)
- You grant the maintainers the right to use, modify, redistribute, and relicense your contribution as part of this project or in closely related projects using a compatible license.
- You confirm that you own the rights to the submitted work and that it does not violate any external copyright or license obligations.

**This is standard practice for open-source repositories and ensures all contributions remain legally consistent**

### 4. No trivial or low-effort PRs
The following PRs will be closed without review:
- Single-typo fixes in README or non-code files
- Stylistic rewrites of documentation
- Pure formatting/whitespace changes
- Variable renames done for personal preference
- "One-line" PRs intended only to count as contributions

**If unsure whether a change is meaningful, open an issue first**

### 5. Follow the project's coding style (even if you don't agree with it)
- Match the existing code style and patterns
- Do not apply automated "optimize imports", "reformat file", or mass cleanup tools.
- Only update formatting where necessary for the functional change.

### 6. Keep PRs focused and small
- One PR = one fix or one feature.
- No combining unrelated edits
- Avoid broad refactors unless approved in advance.

### 7. Discuss major changes beforehand
Open an issue before starting work on anything that:
- Breaks public APIs
- Adds new dependencies
- Alters build configurations
- Modifies core architecture or module layout
- Performs sweeping refactors

**Unexpected large PRs may be closed.**

### 8. Versioning & Changelog rules

**Version Numbers**
- Do not bump the version yourself, unless you have been explicitly told to.
- If your change requires a version bump, mention it in the PR description and maintainers will handle it.

**Changelog Entries**
- Add a short entry under the relevant section of the changelog
- Keep entries concise:
    - Added: Feature X
    - Fixed: Crash in Y
    - Changed: Behavior of Z
- Do not reorder or rewrite other entries

**This keeps release management clean and conflict-free**

### 9. PR description requirements
Every PR must include:
- What was changed
- Why it was changed
- Any migration notes (if relevant)

**PRs without a proper description may be closed**

### 10. Build Instructions

```bash
./gradlew build
```

### 11. Security
DO NOT disclose vulnerabilities in the public PRs or issues. Report them privately to us on discord

---

## 🧩 How to Contribute

1. Fork the repository
2. Create a branch:
  ```bash
  git checkout -b feature/my-change
  ```
3. Make your edits
4. Build and verify
5. Submit your PR with a clear description

---

## Additional Requirements and Notes

1. We use Intellij Idea for all development. If you use a different editor, DO NOT submit your editor configs along with your PR
2. Most of our projects make use of Lombok. You will need to install the `Lombok` plugin inside Intellij Idea to work properly with our code base
